目标：在现有 C++17 businessd 上完成可部署、可恢复、可验收的完整业务产品，最终范围包含 V2 算法任务、人脸底库、通知与硬件联动。本文件是实施方案，本轮未修改业务源码、未执行运行时测试；下面的源码问题来自静态核查，修复时先增加可复现的回归场景。

## 3. 目标结构与数据流

保留 C++17、SQLite、现有 HTTP/WS/UDS 框架，逐步把业务编排从 HttpApi 和 main 搬到服务层，不要求先做大规模框架替换。

    HttpApi / WsServer / HookServer
        → CameraService / TaskService / AlgorithmPackageService
        → ConfigCompiler + ResourceAdmission + Reconciler
        → EngineClient(现 UdsClient) / MediaService(现 ZlmClient)

    engine 事件
        → EventService：规范化、来源校验、去重、事务落库
        → 同事务生成 snapshot / notification / linkage 执行意图
        → 提交后发送 WS；独立 Worker 执行外部调用并更新状态

    face_feature
        → FaceLibraryService：版本检查、比对、多帧确认
        → EventService → 相同通知与联动链路

关键约定：

- SQLite 保存期望配置；运行状态保存 desired_revision、applied_revision、apply_status、last_error。跨 ZLM/UDS 的操作使用持久化操作记录、补偿与对账，不持有 SQLite 写事务等待网络。
- 同通道操作串行；全局资源准入使用一致的预算快照/预留，防止并发请求同时通过旧预算。
- 摄像头源 RTSP 持久化保存原地址；单独生成 ZLM 回环地址供引擎使用，不把源地址覆盖成回环地址。将回环端口纳入业务配置与测试。
- 摄像头在线、引擎通道状态、媒体可播放、任务已应用是不同字段，不合并成一个 online 布尔值。
- 高频 detections 只走内存与 WS；告警、投递、动作、证据任务进入持久化链路。
- 通知保证至少一次投递，采用稳定 event_uid 和投递幂等键；不承诺外部服务与本地数据库之间的“恰好一次”。硬件动作另按设备是否支持命令去重/状态回读定义重试。
- 当前 getSnap 属于近实时截图。精确告警帧证据必须由 engine 提供帧级快照/证据引用接口，不把稍后截图描述为同帧取证。

2. 升级 FakeEngine 为有真实通道集合/应用配置/版本的状态型假件，可注入重复命令、延迟、拒绝、ACK 丢失和中途断线。
3. 输出 API/事件/数据库字典、功能清单、engine 依赖清单、故障矩阵和验收样例。明确旧接口兼容周期。
4. 建立板卡、摄像头、模型包、通知渠道、硬件端点及协议清单，随选型逐项冻结。未确定项不阻塞无设备依赖的业务开发；对应真实驱动与实机验收记录为待选型/待联调，不填“完成”。

验收：现有功能基线可重现；每个新增模块均有输入、输出、状态、失败语义和验收负责人。

### B1：业务可靠性基础（5–7 人日，依赖 B0）

B0+B1 的具体修改顺序、状态/API 兼容与验收矩阵，见同目录《AIBox_businessd第一阶段执行方案_V1.0.md》。

1. 修复 F01–F08、F11；先补能复现问题的测试，再修改实现。
2. 提取 CameraService、统一配置编译/预检函数，Camera PUT、旧 algos API、SYNCING 共用，避免三份下发逻辑漂移。
3. 新增配置操作表与对账 Worker，处理 add/edit/disable/delete；仅回滚本次创建资源，失败保留目标配置与错误状态。
4. 处理“已有通道”和 ACK 丢失：优先使用 engine 幂等 upsert 或查询配置版本；若暂用 remove/add 重建，完整恢复算法并明确短暂检测中断。
5. 修复 Txn 持锁与提交结果，统一 Worker 生命周期、启动回滚和退出超时；分离 liveness、服务 ready、engine 同步与降级状态。

验收：分别重启 businessd、engine、ZLM，摄像头配置最终一致；两个并发配置请求不穿透预算；启动失败不 abort；旧接口返回与实际状态一致。

### B2：V2 算法任务与规则（7–10 人日，依赖 B1 与 E1/E2）

1. 建 capabilities、algorithm_tasks、task_cameras、task_algorithms、task_rules、task_schedules；规则含稳定 ID、版本、ROI/标定引用及来源。
2. 把已有 camera_algos 迁移为 legacy 任务；新模型成为唯一可写权威。旧 /cameras/{id}/algos 通过适配层修改 legacy 任务，不能另外维持一份可写配置。
3. ConfigCompiler 按摄像头合并全部启用且处于时间窗内的任务，去重物理模型，保留每条规则的 task_id/rule_id、阈值、帧率、类别、ROI 与冷却语义。
4. 相同模型服务多任务时，推理工作量共享，但不同任务的阈值/采样/规则要求不得互相覆盖；这一语义需要 engine 配合。预检按最终编译后的 steady/triggered 核预算与模型依赖计算。
5. 加入参数校验、模板版本、能力可用性校验、任务预检、启停、应用状态、失败诊断、时间计划。时区明确保存并测试跨日/周计划。
6. 对 LINE_CROSS、COUNT、ABSENCE、LOITERING、PROXIMITY、SPEED、COMPOUND、REF_GEOMETRY 等类型建立逐项支持矩阵；业务只放开引擎已验收项。

验收：同一摄像头至少两个任务共享一个模型，各有独立 ROI/规则，事件来源正确；停用一个任务不影响另一个；时间窗、重启、规则修改、预算拒绝均正确。

### B3：事件、证据与存储闭环（4–6 人日，依赖 B1；与 B2 部分并行）

1. 提取 EventService，增加 event_uid、task_id/rule_id、任务/规则版本快照、级别、处置状态、important、证据状态与操作历史。
2. 实现未处理、已确认、处理中、已处理、已忽略五态，以及合法流转、并发版本校验、批量处置、详情、游标分页与统计。
3. 同事务写事件与快照/通知/联动意图；提交后推含本地事件 ID 的 WS 事件。截图就绪后补发 event_updated。
4. 快照任务 pending/running/ready/failed，支持超时、重试、过期与重启恢复；图片先临时文件，再原子完成，数据库与文件定期对账。
5. segments 使用规范化路径等稳定唯一键幂等 upsert；只在删除成功或文件已不存在时删除索引，限制清理到配置存储根目录。
6. 事件、快照、录像、日志、投递记录分开配置保留策略；保护重要/未处置证据，存储压力下先暂停新增快照并报告状态，不静默删除受保护证据。

验收：重复 Hook/事件不重复建档；磁盘满、目录只读、unlink 失败、截图超时可定位；任务删除后历史来源仍可读；告警入库不等待截图。

### B4：人脸底库与识别（6–9 人日，依赖 B2/B3 与 E3）

1. 建人员、名单、样本、特征、提取任务与识别记录；向量保存模型 ID/版本/维度/预处理版本/质量，维度从模型契约取得，不写死。
2. 支持人员与名单管理、图片上传/删除、批量导入、异步提取、冲突/失败原因、启停和重建特征；注册图片提取交给 engine。
3. 提取状态为 pending/extracting/usable/conflicted/failed，恢复时重新领取未完成任务；无人脸、多脸、低质量等情况明确返回。
4. 实现同版本向量比对、阈值和 top1 判定、多帧确认、track 去重、陌生人及黑白名单事件；模型升级后不混比旧版本向量。
5. 识别事件使用共同 EventService，走相同通知、证据和联动链路；底库变更具有版本和审计记录。

验收：真实模型完成“注册图片→特征可用→视频识别→事件→通知”；已知/陌生/黑白名单均验证，记录测试集与阈值结果；性能按实际底库规模实测，不无依据承诺识别准确率。

### B5：通知中心与真实云投递（4–6 人日，依赖 B3）

1. 建 notification_channels、notification_routes、notification_deliveries；路由按摄像头/任务/类型/等级/名单/时段匹配。
2. MQTT 适配器接入真 Broker，以 PUBACK 作为确认，维护消息 ID 与投递记录映射；Webhook 支持超时、响应检查和稳定幂等标识。增加渠道测试与连接状态。
3. 持久化投递状态、attempt、next_retry_at、last_error、expires_at；支持退避、重试上限、死信、手工重试和渠道隔离。
4. ACK 后事务更新投递/事件上报状态；多渠道情况下由策略决定 reported 的聚合含义，不能收到一个 ACK 就视为全部送达。
5. 明确是否等待证据就绪、等待多久、无截图是否发送；停用渠道与历史待发记录的处理策略可见。

验收：发送前、已发送未 ACK、ACK 后未落库三个故障点都可恢复；断网后补投；坏渠道不阻塞其他渠道；外部可能收到重复消息时能按 event_uid 去重。

### B6：硬件联动（4–7 人日，依赖 B3；与 B5 并行）

1. 建 linkage_endpoints、linkage_rules、linkage_actions 和端点目标状态；规则引用事件/任务/名单与可选外部输入条件。
2. 定义 EndpointAdapter：连接、读取状态、执行、保持/释放、错误反馈。实现已选设备的 GPIO、RS485/Modbus、网络语音驱动与 FakeAdapter。
3. 每个端点串行执行；动作包含唯一 command_id、TTL、冷却、保持时间、优先级、取消/解除和执行记录。
4. 重启后先核对目标状态与设备实际状态，按设备能力恢复；已过期声音/脉冲不直接重放。设备不支持命令去重时，不宣称物理动作恰好执行一次。
5. 提供端点测试、活动输出、故障状态与人工全部解除；外部设备调用不得阻塞 UDS 或事件事务。

验收：重复事件、同时触发、设备离线、超时、进程重启、保持后释放均验证；实板观察输出与状态回读，设备协议/接线记录进入交付材料。

### B7：产品接口、算法包与运维（8–12 人日，依赖 B1；后段与 B4–B6 并行）

拆为 B7a 权限与统一文件访问 3–4 人日、B7b 算法包导入/升级/回滚 3–5 人日、B7c 配置/诊断/备份/部署 2–3 人日；不可把这些新增功能作为几项简单接口一并估算。

1. HttpApi 按业务域拆路由文件；统一参数校验、分页/排序、错误码、权限、配置导入导出。新长任务返回 operation_id/pending，旧接口保留兼容语义。
2. 完成初始化、会话与 admin/operator/viewer 权限；同一访问策略覆盖 REST、WS、截图和录像。密钥不在普通查询/日志中返回，移除示例中的固定生产凭据。
3. AlgorithmPackageService 完成离线上传、目录/平台/清单校验、暂存、原子切换、engine 自检确认、版本历史与显式回滚。当前 reload 不等价于用户选择旧版本，需补齐该区别。
4. 汇总 UDS、ZLM、配置版本、任务、队列、投递、端点、磁盘与版本信息；日志携带 event_uid/task_id/rule_id/action_id；提供诊断包及一致性备份恢复。
5. 提供配置样例、systemd 单元、安装/升级/回滚脚本、依赖版本清单；配置校验失败应给明确原因。

验收：选定的 Web 页面全部接真实 API；未配置/不可用与模拟状态明确显示；未授权不能通过 WS 或文件直链绕过；导入失败不破坏旧配置，恢复后状态可重建。

### B8：整体验收与交付（业务开发投入 3–5 人日，依赖 B2–B7 与 E1–E4）

此处人日计验收脚本、缺陷修复与开发联调支持。独立测试人员的执行、巡检和报告投入在第 8 节另外列出；72 小时稳定性是经过时间，不等价于 3 人日连续操作。

1. 新增 smoke_business_full，按功能输出 PASS/FAIL/SKIP 和原因，区分 Fake、真 ZLM、真 Broker、真模型、真硬件。
2. 做 businessd/engine/ZLM 单独重启、UDS 闪断、ACK 丢失、数据库写失败、磁盘满、慢 WS、Broker/外设离线故障矩阵。
3. 在冻结的摄像头数、任务数、底库量、事件峰值、通知渠道和端点规模下跑 72 小时；在 B0 确定资源/延迟阈值，观察队列、RSS、FD、投递和动作状态是否收敛。
4. 验证旧库迁移、配置备份恢复、算法包失败回滚、安装升级与版本回退。数据库回退用兼容程序或备份恢复，不假设向下迁移永远可行。

验收：最终配置中的必选真实链路不得 SKIP；未接模型或设备项在交付清单中明确未验收，不用接口返回成功代替真实效果。

## 5. 必须同步推进的 engine 接口依赖

| 编号 | 最小交付 | 阻塞的业务功能 |
| --- | --- | --- |
| E1 | 协议版本与能力声明；明确已有通道/upsert 语义；配置 revision 的 ACK/查询；注册表含真实规则、post、级联与标定支持 | 可靠重连、资源预检、任务能力准入 |
| E2 | 一台摄像头多任务的配置结构；规则级 task_id/rule_id；融合、按 cam+algo 跟踪隔离、所需规则与时间驱动 | V2 任务真实运行和来源追溯 |
| E3 | face_feature（session、request、cam/task/rule/track、模型版本、维度、时间、质量）；异步注册图片提取；必要级联与关键点 | 人脸注册与识别闭环 |
| E4 | 事件 session_id/sequence 或稳定 event_uid；精确证据引用（如要求）；命令/事件兼容测试 | 可靠去重、帧级证据及断线事件补偿 |

设计稿的 set_algos 顶层单一 task_id 不足以表达一摄像头多个任务：协议冻结时必须改为任务数组或规则级来源标识。业务不能仅增加几个表就宣称已支持 V2。

UDS 当前事件是尽力而为。本方案事务保障的是已进入 businessd 的事件与执行意图。若验收要求 UDS 断线期间也不丢告警，需要 E4 增加确认、有限重放及缺口观测；engine 崩溃前尚未交给业务持久化的事件，仍需单独定义恢复边界。

职责分配：engine 负责检测、融合、几何规则、级联与特征提取；businessd 负责任务/时间窗、名单与持久化、身份比对、事件处置、通知、硬件外设及跨通道业务关联。Web 负责配置与展示，并消费真实状态。

## 6. 建议目录与数据迁移

逐步新增 business/services/{camera_service,task_service,config_compiler,reconciler,event_service,evidence_service,face_library_service,notification_service,linkage_service,algorithm_package_service}，business/adapters/ 放 MQTT/Webhook/外设适配器，business/workers/ 放持久任务领取与执行；具体文件拆分可随实现调整。

数据库按工作包追加迁移，保留历史脚本：

1. 配置操作/revision、设备启停与删除状态。
2. 任务、规则、能力、时间计划与 legacy 数据转换。
3. 事件来源/处置历史、证据任务、录像去重约束。
4. 人员、名单、特征与提取任务。
5. 通知渠道/路由/投递和硬件端点/规则/动作。
6. 初始化/权限、审计、配置与版本记录。

先用旧库副本测试重复迁移、异常中断与数据保留；敏感配置和外部路径由专门导入导出逻辑处理，不能原样导出为公开配置。

## 8. 排期、并行方式与启动顺序

工作包估算为有效业务开发人日，包含模块级回归、验收脚本和开发联调支持，不含新模型训练、engine V2 实现、独立前端开发、独立测试执行、外设等待和额外云研判。B0–B8 合计约 42–64 人日，实际复杂度以 B0 复现结果和接口冻结为准。

建议资源：2 名 C++ 业务开发、1 名前端、1 名测试/板端联调，并安排 engine 开发并行交付 E1–E4。前端另预留约 12–18 人日，独立测试人员从模块集成到 B8 的执行/巡检/报告另预留约 8–12 人日；后者包含其在 B8 的工作，并非在 B8 之后再追加一轮同样验收。不能把 backend 人日简单除以人数当作日历工期。

可执行的依赖顺序：

    B0 → B1
         ├→ B2（还需 E1/E2）
         └→ B3 → B5 / B6
    B2 + B3 + E3 → B4
         B7 随契约与基础修复分段推进
    B2–B7 + 必需 engine 接口 + 真实模型/Broker/设备到位 → B8

按上述人员与设备/engine 同步到位的前提，完整产品日历排期可先按 8–12 周估算；单人还需承担前端、测试或 engine 时必须重新排期。当前设备与渠道尚未确定，42–64 人日和 8–12 周仅为参考场景估算；真实驱动数量、协议复杂度与设备等待时间确定后重新核算，不能作为已冻结的交付承诺。

第一周建议交付：

- 第 1–2 天：基线、接口/设备清单、状态型 FakeEngine，冻结多任务与事件来源契约。
- 第 3–5 天：修复停用算法、通道重建丢配置、已有通道重连、Txn 与启动退出问题；搭建 CameraService 与对账骨架。
- 周末验收：“只重启 businessd，保留 engine/ZLM，现有摄像头和规则恢复；改流地址后算法配置仍在；禁用算法确实不执行”。

每个工作包交付：代码、追加迁移、API/状态定义、失败场景测试、实际运行报告及界面验证记录。必选真实链路未通过，工作包不标记完成。
