# AIBox 远程域名访问与摄像头发现业务需求 V1.0

- 整理日期：2026-10-30
- 适用项目：AIBox 独立式三进程架构
- 主要涉及模块：businessd、Web 前端、ZLMediaKit 及部署网络
- 文档状态：需求整理稿，供负责人确认与开发拆解
- 核查说明：现有能力依据当前仓库源码整理，不代表已完成本轮测试或实机验收。

## 1. 需求背景与目标

项目负责人提出两项业务要求：

1. 用户通过固定域名远程访问 AIBox，不再要求用户在盒子现场使用本地地址访问。
2. 用户通过扫描发现摄像头 IP，选择设备后完成摄像头连接，减少手动填写取流地址的操作。

已确认第一项的访问范围为：**在外网通过域名远程访问一台 AIBox**。

本次目标是形成“远程访问 → 现场摄像头发现 → 设备接入 → 视频预览与任务操作”的完整业务流程。

## 2. 需求范围与边界

| 项目 | 本次范围 |
| --- | --- |
| 访问对象 | 一台 AIBox |
| 访问方式 | 从外网通过固定域名访问，正式入口采用 HTTPS |
| 远程功能 | 访问管理页面、配置摄像头与任务、观看视频、接收告警、查询事件和播放录像 |
| 扫描执行位置 | 由 AIBox 在其所在现场网络中执行，浏览器负责发起请求和展示结果 |
| 摄像头连接 | 选择发现的设备，提供凭据，获取或补充取流地址，保存配置并验证拉流 |
| 保留方式 | 保留手动添加摄像头能力，兼容无法自动发现的设备 |

以下内容不自动纳入本次范围：多盒子统一管理平台、多租户管理、任意跨网段自动发现、摄像头自动改 IP、摄像头密码找回或绕过认证。

“周围摄像头”指 AIBox 所连接网络中可发现、可通信的摄像头，不以物理距离为判断依据。扫描网段与跨 VLAN 能力以现场路由和网络配置为准。

## 3. 需求一：固定域名远程访问

### 3.1 用户使用流程

```text
用户在外网打开固定域名
    → 完成身份认证
    → 查看 AIBox 与摄像头状态
    → 配置摄像头和分析任务
    → 观看实时视频、接收告警
    → 查询历史事件和录像
```

域名示例：`https://aibox.example.com`。该地址仅用于说明，实际域名尚未确定。

### 3.2 功能要求

| 编号 | 要求 | 业务说明 |
| --- | --- | --- |
| R01 | 固定域名入口 | 用户无需输入现场局域网 IP；入口对应指定的一台 AIBox |
| R02 | 外网可达 | 在不连接现场局域网的条件下，能够访问该入口 |
| R03 | 管理操作 | 页面、摄像头管理、任务管理和已有查询功能通过入口正常使用 |
| R04 | 实时消息 | 检测框、告警、设备状态等 WebSocket 消息可正常接收 |
| R05 | 实时视频 | 宫格和单路预览可正常播放，分别验证信令和实际媒体连接 |
| R06 | 历史证据 | 事件截图与录像可通过授权后的远程入口访问 |
| R07 | 访问控制 | API、WebSocket、截图和录像采用一致的授权策略，具体登录方案待确认 |
| R08 | 断线提示与恢复 | 网络中断或盒子离线时显示明确状态；网络恢复后可重新连接，配置结果可查询 |

通过域名访问不等于已打通外网连接。实施时必须同时解决域名解析、入口可达、反向代理和视频媒体通路。

### 3.3 部署方案与待选项

| 现场条件 | 可选方案 | 需要落实的事项 |
| --- | --- | --- |
| 有可入站访问的公网地址，且允许配置路由器 | 域名解析到公网入口，配置必要映射与反向代理 | 公网地址稳定性、证书、端口、路由与防火墙 |
| 无可入站访问的公网地址 | 公网服务器提供入口，AIBox 主动建立隧道 | 服务器、隧道连接与恢复、媒体直连或中继能力 |

在现场网络条件尚未确定时，可优先评估“公网入口 + 盒子主动建立隧道”。这是建议方案，不代表公网服务器、隧道产品或媒体中继已经选型。

业务服务继续运行在 AIBox 上。公网入口负责接入与转发；若媒体采用中继，还需评估服务器带宽和并发容量。

### 3.4 现有基础与改造点

| 位置 | 现有基础或限制 | 需要完善 |
| --- | --- | --- |
| `web/api.js` | REST 请求采用相对路径 | 验证统一入口下的 API 路由与认证 |
| `web/ws.js` | 当前拼接 `ws://主机:端口` | 支持 HTTPS 对应的 WSS，支持通过统一入口代理 |
| `business/http_api.cpp` | 视频信令和录像 URL 当前拼接 HTTP 地址，信令包含 ZLM 端口 | 生成浏览器从外网可达的地址，正确处理 HTTPS 与代理入口 |
| `business/main.cpp` | 已有基础 Token 与监听地址配置 | 明确并接通完整远程授权链路 |
| 部署文件 | 当前未看到完整域名入口配置 | 补充反向代理、证书、所选隧道及运行恢复配置 |
| ZLM | 已有 WebRTC 播放信令对接 | 按实际部署配置可达地址、媒体端口或中继链路 |

HTTP/HTTPS 信令代理和 WebRTC 媒体传输分别验证。页面能打开、接口返回成功，不作为视频链路验收通过的依据。

### 3.5 验收标准

1. 手机关闭 Wi-Fi，使用移动网络打开正式域名，完成认证。
2. 摄像头列表、任务配置与系统状态可正常查看和操作。
3. 摄像头预览可出画面，检测框与实时告警能够接收。
4. 事件截图可查看，已有录像可检索和播放。
5. 未授权访问 API、WebSocket、截图和录像均按统一策略处理。
6. AIBox 或隧道重连后，用户可恢复访问；离线期间页面给出明确状态。
7. 浏览器实际请求使用外网可达地址，HTTPS 页面没有由内部 HTTP/WS 地址导致的混合内容问题。

## 4. 需求二：摄像头扫描发现与连接

### 4.1 用户使用流程

```text
用户在本地或远程页面点击“扫描网络”
    → AIBox 在选定的现场网卡和扫描范围内发现设备
    → 页面展示发现结果与已有设备状态
    → 用户选择摄像头，输入账号和密码
    → 获取主、子码流地址，必要时手动补充
    → 保存配置并建立视频代理
    → 检查拉流与预览结果
```

远程用户的浏览器不直接扫描摄像头网络。即使增加公网入口，发现、认证和取流仍由现场 AIBox 完成。

### 4.2 功能要求

| 编号 | 要求 | 业务说明 |
| --- | --- | --- |
| C01 | 发起扫描 | 支持用户主动扫描，展示当前扫描网卡和范围 |
| C02 | 设备发现 | 使用 ONVIF 发现，并通过受限的网段探测补充发现结果 |
| C03 | 展示结果 | 至少显示 IP、发现方式、设备服务地址和是否已添加 |
| C04 | 提供凭据 | 用户选择设备后输入账号密码，认证失败可修改并重试 |
| C05 | 获取取流地址 | ONVIF 可用时获取主、子码流；仅发现 RTSP 服务时允许补充路径 |
| C06 | 接入验证 | 分别显示配置保存、应用进度和实际拉流结果 |
| C07 | 去重与状态 | 同一次扫描结果去重，对已添加设备做明确标记 |
| C08 | 过程与失败反馈 | 展示扫描中、无结果、超时和失败信息，避免重复点击造成扫描堆积 |
| C09 | 手动添加 | 对无法发现、非标准端口等情况保留手动接入入口 |

扫描命中只表示发现候选设备或协议服务。端口开放及厂商路径推测不作为品牌确认或接入成功的依据。

### 4.3 已有实现

| 模块或接口 | 当前源码中的能力 |
| --- | --- |
| `business/onvif_client.cpp` | 多网卡 WS-Discovery 探测、HTTP ONVIF 补充探测、RTSP 服务探测 |
| `POST /api/cameras/scan` | 返回发现设备的 IP、服务地址和类型等信息 |
| `POST /api/cameras/onvif_uri` | 根据设备地址和凭据获取主、子码流地址 |
| `POST /api/cameras` | 保存摄像头配置，进入既有配置应用流程 |
| `web/app.js` | 已有“扫描网络”、结果卡片、凭据输入和添加流程 |

因此，本项主要是完善和验证已有链路，无需从零开发发现模块。

### 4.4 当前限制与补充工作

1. 当前补充扫描按各网卡 IP 所在的 `/24` 范围生成目标，尚未按实际掩码或用户选择完整控制扫描范围；需明确允许的目标范围、并发与超时。
2. 当前扫描接口同步返回结果；应完善进度和重复请求控制，是否采用异步扫描任务在实现设计时确定。
3. ONVIF 发现可能受设备发现开关、组播配置、网段隔离等影响；默认端口探测也无法覆盖所有非标准端口设备。
4. 对普通 HTTP 服务的认证响应、RTSP 服务和疑似厂商特征，需要通过后续协议交互确认，减少误判。
5. 页面需要区分“已发现、认证失败、取流失败、配置已保存、等待应用、连接成功”等状态。
6. 发现机制需在实际 AIBox 网络接口与真实摄像头上验收；Docker 编译测试和模拟网络测试不能代替现场发现测试。

### 4.5 验收标准

1. 使用预先准备的真实摄像头，在约定网络与协议条件下，不手动填写 IP 即可通过扫描发现。
2. 已添加设备被正确标记，同一次扫描结果无重复项。
3. 选择 ONVIF 摄像头，输入正确凭据后获取取流地址并完成接入，预览可出画面。
4. 错误凭据返回明确提示，不将设备显示为连接成功；修正后可以重试。
5. 仅发现 RTSP 的设备可按提示补充地址；无法发现的设备可手动添加。
6. 在无设备、设备离线、多网卡和重复发起扫描等场景下，扫描能结束并给出合理状态。
7. 从外网域名页面发起扫描，发现的是 AIBox 现场网络中的设备，后续接入和预览可完成。

## 5. 开发工作拆解与建议顺序

| 阶段 | 工作内容 | 交付物 |
| --- | --- | --- |
| 1. 条件确认 | 确认域名、现场网络、公网入口、摄像头与扫描范围 | 网络拓扑、配置清单、验收设备清单 |
| 2. 现场接入 | 核验现有扫描、凭据认证、取流、代理创建和预览，补齐状态反馈 | 接入功能与真实摄像头测试记录 |
| 3. 远程管理 | 接入 HTTPS 域名入口，完成 API、WS、文件访问和授权适配 | 部署配置、相关代码及远程管理测试记录 |
| 4. 远程视频 | 打通信令与媒体连接，确定直连或中继方案 | 实时播放、告警和录像验证记录 |
| 5. 联合验收 | 外网扫描现场摄像头、添加设备、配置任务、接收告警，并验证断线恢复 | 验收报告、部署与恢复操作说明 |

业务层主要承担发现与接入编排、配置状态、对外地址生成和接口；前端承担操作与状态展示；部署人员落实域名、证书、隧道和网络规则；媒体链路需要与 ZLM 配置共同联调。

## 6. 待负责人或现场确认的事项

| 待确认项 | 需要明确的内容 |
| --- | --- |
| 正式域名 | 域名归属、解析管理权限、证书管理方式 |
| 公网条件 | 是否有可入站公网地址，能否配置路由器及防火墙 |
| 公网服务器 | 是否已有服务器，是否允许部署隧道与媒体中继 |
| 访问认证 | 使用现有 Token、独立登录还是公司统一认证 |
| 现场网络 | AIBox 网卡、相机网段、VLAN、组播和路由条件 |
| 验收摄像头 | 品牌型号、ONVIF/RTSP 支持、端口、账号和密码 |
| 性能要求 | 扫描最大范围、完成时间、远程观看并发数、视频延迟与带宽预算 |
| 部署形态 | businessd 在板上直接运行还是容器运行，所需网络如何接入 |

以上条件尚未全部确定，本文不承诺固定交付工期或全部型号摄像头的兼容性。
