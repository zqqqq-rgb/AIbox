# AIBox 同价位产品竞争力与体验优化建议 V1.0

- 整理日期：2026-10-30
- 依据：厂家/供应商公开资料、当前项目源码、已保存竞品页面与 API 快照
- 适用目标：提高同等交付成本下的部署体验、有效功能覆盖和运行可维护性
- 当前前提：目标整机售价、算法授权范围、存储配置和首批客户尚待确认；先按现有 RK3588 架构及单站点监控改造设计产品路线。
- 证据边界：公开规格属于厂家或供应商声明，未实测竞品；本文的体验指标是建议目标，不是本项目已达到的结果。

## 1. 产品定位建议

建议先聚焦小型工厂、仓储等已有摄像头的单站点：用户接入现有设备，选择业务场景，配置区域和时间，收到可核实、可处置的告警，并可远程维护。

建议产品主张：

> 10 分钟内完成首路接入并验证首个告警；日常操作简单，告警有证据，故障可定位，恢复少依赖人工。

“10 分钟”需要在兼容摄像头、凭据正确、网络可达等条件下通过用户测试验证，再决定是否写进销售承诺。

“同价位体验最好、功能最丰富”作为内部竞争目标。对外比较需要相同配置、场景与测量方法的证据，目前不能认定已达到。

### 2.2 应使用的同价位口径

```text
三年使用总成本
  = 整机与存储
  + 必需算法授权/续费
  + 部署与调试
  + 必需远程服务与中继流量
  + 维护、升级与售后
```

每个竞品用同一张报价单核对：可连接相机数、同时分析路数、每路模型组合、分析 FPS、已含场景、录像范围、授权期限和远程服务费用。

厂家已公开提供多算法、时段布控和浏览器管理，因此当前项目应把这些纳入完整交付设计。差异化重点放在首次接入、任务配置、告警核实、运行恢复和维护成本。

## 3. 当前项目可以利用的基础

1. 已有摄像头扫描、ONVIF 取流、ZLM 编排、WebRTC 预览和录像查询。
2. V2 后端已有草稿、无时间计划任务启停、跨摄像头部署及状态查询；前端尚缺独立任务页面。
3. 配置使用目标版本、确认版本、操作记录与 Reconciler，具备继续建设恢复能力的基础。
4. 已有事件及任务/规则来源持久化，可以扩展证据、处置和通知闭环。
5. 已有 Fake、Mock、子进程恢复测试，可以验证更多失败场景。

需优先补齐的基础：初装与统一认证、外网地址适配、WS/证据授权、任务页面、证据任务持久化、真实通知和可部署的服务管理。

## 4. 体验设计：围绕六个用户流程建设

### 4.1 首次开箱与远程接入

推荐流程：激活设备 → 设置管理员 → 检查网络与时间 → 扫描摄像头 → 验证首路视频 → 创建首个任务。

- 使用固定 HTTPS 入口，远程认证与设备绑定关系明确。
- 页面、API、WSS、截图和录像统一入口与授权策略。
- 本地分析和现场管理在外网不可用时仍能工作；远程功能显示具体连接状态。
- 公网入口、隧道和 WebRTC 媒体路径分别验证。
- 管理页面不返回摄像头密码，敏感配置查询时脱敏。

当前代码中空 Token 放行、WS 握手未见统一认证、录像直接静态挂载等问题，应与外网访问功能一起解决后再部署公网入口。

### 4.2 摄像头接入向导

- 扫描前显示可选网卡和范围，扫描中显示进度，限制重复任务。
- 结果展示 IP、协议、已添加状态；开放端口仅作为候选信号。
- 支持批量选择、批量凭据填写与逐台认证结果；凭据不展示在结果列表。
- 添加前测试取流，区分网络不通、账号错误、地址错误和视频编码不支持。
- 已添加设备不重复创建；保留手工 RTSP 添加。
- 相机 IP 变化后的识别与恢复，作为后续能力设计；需要可靠设备标识，不仅依赖 IP 去重。

### 4.3 场景化任务向导

推荐步骤：选择业务场景 → 选择摄像头 → 在画面上配置区域/线 → 选择时间 → 预检与试运行 → 启用。

- 默认界面使用业务语言，如“进入禁区”“停留超过 20 秒”。
- FPS、模型阈值等保留在高级设置，并提供合理默认值。
- 提交前显示模型依赖、资源占用和预计受影响的摄像头。
- 提交后区分“已保存、正在应用、已运行、失败或部分失败”，允许查询进度。
- 增加试运行模式：观察检测和规则触发，不直接发送正式通知或驱动外设；这是待开发功能。
- 有明确状态与版本后再支持复制任务、批量调整，保留逐摄像头结果。

### 4.4 告警工作台

- 实时告警、待处理列表、事件详情形成连续流程。
- 同一事件提供触发原因、时间、任务、截图和对应录像入口。
- 处理、忽略、重要标记、备注和处理历史有持久记录。
- 截图和录像状态可见；缺失时显示原因，后台持久重试。
- 引入事件聚合、冷却和生命周期，减少同一持续问题反复刷屏；去重键和重启行为需明确。
- 提供误报标记和样本导出，先建立人工复核流程；模型更新通过对比验收后发布。
- 云端 AI 复核可后续选配，保留超时、费用和原始事件状态。

### 4.5 用户看得懂的故障诊断

在摄像头或任务详情展示：

```text
相机连接 → 视频可用 → 模型运行 → 规则生效 → 证据生成 → 通知到达
```

失败时给出可执行建议，如“摄像头密码不正确”“当前不在布防时段”“模型未安装”“任务等待应用”“截图获取失败”。

复用现有队列、通道、配置操作与引擎状态；日志包含关联标识，但界面优先展示用户能理解的状态。

### 4.6 手机与远程维护

- 手机浏览器优先支持告警查看、证据播放、任务启停和状态检查。
- 复杂 ROI 编辑保留桌面端优化，不要求所有管理工作都挤进手机界面。
- 支持配置备份恢复、诊断包、版本与模型历史、失败更新回退。
- 事件导出和临时分享采用受控访问，敏感字段从诊断包中脱敏。
- 提供常驻服务、开机启动、日志轮转、健康检查和恢复说明。

## 5. 功能丰富度：按可验证的场景组合扩展

### 5.1 第一层：所有配置都应完整提供的基础功能

设备管理、扫描/手动接入、实时预览、任务管理、规则编辑、事件与证据、录像查询、基础通知、状态诊断、备份恢复和开放 API。

功能是否收费、是否包含存储和远程服务，应在报价中列明。

### 5.2 第二层：共享人员检测输入的规则模板

| 场景 | 当前基础 | 新增依赖 |
| --- | --- | --- |
| 区域进入/入侵 | 当前 V2 业务已开放 `region_in` | 完善页面、试运行和真实告警验证 |
| 驻留超时 | 当前 V2 业务已开放 `dwell` | 完善参数、排班、证据和恢复验证 |
| 越线与方向 | 引擎/跟踪可作为基础 | 新规则、方向定义、边界防抖和业务准入验证 |
| 区域人数超限 | 可共享人员检测结果 | 计数语义、持续时间、遮挡场景测试 |
| 岗位无人 | 可共享人员检测结果 | 时间计划、持续无人计时，断流与无人必须区分 |
| 徘徊 | 可共享检测与跟踪 | 轨迹规则、阈值、视角适用条件和误报验证 |

共享模型可降低新增规则的推理负担，但规则开发、跟踪质量与验证仍需投入。后四项不能提前标记为可用。

### 5.3 第三层：随客户需求引入专用模型

PPE、姿态/跌倒、烟火、抽烟、人脸、车牌等按首批客户价值排序。每项须验证：

- 模型来源、商用范围、平台兼容与输入要求。
- 场景适用条件、目标尺寸、角度、光照和遮挡表现。
- 真实误报/漏报、事件证据、算力与内存影响。
- 任务启停、并发、重启恢复和版本回退。

建议先确定一个专用模型组合，例如在人员区域规则稳定后增加 PPE；具体选择由客户样本和模型效果决定。

### 5.4 第四层：通知与联动

- 首先交付一个实际使用的通知渠道，连同测试发送、状态、失败重试一起交付。
- 标准 Webhook 可作为系统集成基础，再按客户选择企业消息渠道或 MQTT。
- 事件与投递意图同事务保存，重启后继续执行；对重复投递提供稳定事件标识。
- 外设按实际选型接入，提供保持/释放、超时、人工解除与动作记录。
- 端点和通知失败不阻塞事件保存与其他渠道。

## 6. 容量、成本与授权策略

### 6.1 发布可复现的容量表

接入路数、解码路数、同时分析路数和任务数分别列出。将候选 4 路、8 路方案放入实测，验证后再确定销售档位。

| 必测维度 | 需记录内容 |
| --- | --- |
| 视频 | 编码、主子码流、分辨率、视频 FPS、码率 |
| 分析 | 模型版本、精度、每路模型组合、目标与实际分析 FPS |
| 规则与告警 | 规则数、事件峰值、持续条件、通知渠道 |
| 并行负载 | 录像、预览客户端数、截图、远程观看和磁盘写入 |
| 结果 | 告警延迟、证据完成率、排队与丢弃、温度、RSS/FD 和恢复情况 |

任务超预算时，说明原因并建议降低分析频率、减少重模型或调整任务分配。不能将静默降级后的输出仍展示成原承诺性能。

### 6.2 控制远程服务成本

- 本地分析、事件保存和现场处置持续独立运行。
- 远程默认传输状态、告警摘要和按需证据；视频在用户观看时传输。
- 本地直连和远程中继分别评估，远程能力需要可持续的带宽预算。
- 示例：一路 2 Mbps 视频观看 1 小时约产生 0.9 GB 数据，不含协议开销。

### 6.3 透明授权

在模型与组件许可允许、成本可承担的前提下，建议将核心本地功能和基础场景随设备提供清晰、稳定的使用权。远程中继、云端复核、定制模型和现场服务单独写明费用。

若采用订阅，明确到期后哪些服务停止、哪些本地功能仍可使用，提供数据导出和迁移方式。不得将“支持全部算法”解释为所有算法可同时满速运行。

## 7. 体验与质量验收建议

以下为内部目标草案，需通过试用与实测冻结：

| 指标 | 建议目标或定义 |
| --- | --- |
| 首次接入与告警 | 在约定网络、兼容相机和正确凭据下，首次用户 10 分钟内完成首路接入并验证告警 |
| 创建常用任务 | 默认模板下，受试用户 3 分钟内完成配置，不需要修改模型高级参数 |
| 核实告警 | 从通知到关键证据不超过 3 次主要操作 |
| 页面/API 响应 | 本地普通查询 P95 小于 1 秒，排除扫描、录像下载等长任务；长任务提供进度 |
| 证据可靠性 | 在定义的正常负载下，证据完成率以 99% 为初步目标，分母为要求证据的已保存事件；失败原因和重试状态可查 |
| 告警质量 | 对每个场景标注测试集，记录事件级 precision、recall 和每相机日误报数；阈值按业务损失与客户容忍度确定 |
| 恢复能力 | 注入相机断线、网络闪断、引擎/业务单独重启，记录恢复耗时与失败数；不将断线期间事件保证混同为配置恢复 |
| 稳定性 | 在冻结负载下完成 72 小时连续测试，检查队列可收敛、内存与 FD 无持续异常增长、已保存任务和执行意图可恢复 |

任何准确率和延迟目标均需与视频条件、事件定义、持续时间、负载和网络条件一起发布。

## 8. 版本推进顺序

| 阶段 | 重点 | 完成条件 |
| --- | --- | --- |
| V1：可交付 | 初装认证、摄像头向导、HTTPS/WSS 远程入口、V2 任务页、事件详情与持久证据、一个真实通知渠道 | 一条真实客户流程完整通过；未授权请求不能绕过访问；主要故障可定位和恢复 |
| V1.1：易用且丰富 | 时间计划、批量配置、试运行、事件处置、规则模板扩展、任务指标、备份与诊断 | 用户试用完成体验目标，新增规则和恢复矩阵通过 |
| V1.2：行业扩展 | 选定专用模型、外设联动、模型包导入回退、样本反馈 | 各场景有数据、容量和实机验收记录，报价清楚列明边界 |

优先完成已有 C++ 业务基础上的闭环。暂不把整套 Python 重写、多租户云平台、跨镜 ReID、多模态持续分析和全量算法目录作为首版前置条件。

## 9. 怎样验证同价位优势

选取 2–3 台取得同条件报价的竞品，使用相同摄像头、视频、场景、网络和并发负载，开展可重复测试。对接入和日常任务安排首次使用者参与。

建议评分权重草案：

| 项目 | 权重 |
| --- | --- |
| 初次部署与接入 | 20% |
| 日常任务与告警操作 | 15% |
| 告警质量及证据 | 25% |
| 稳定性与故障恢复 | 15% |
| 可验证业务场景覆盖 | 15% |
| 三年总成本与授权清晰度 | 10% |

可验证场景必须具备实际模型/规则执行、事件证据、操作与恢复记录。目录中的占位项不计分。

取得同条件的测试和成本数据后，再使用具体表述，例如“在指定相机和场景下，首次部署用时更短、误报更少、故障恢复更快”。

## 10. 下一轮需要冻结的产品信息

1. 整机含税售价，以及是否含存储、电源、算法和远程服务。
2. 第一类客户和必须解决的 2–3 个业务场景。
3. 可获得的真实摄像头、板卡、模型及测试视频。
4. 候选路数、分析频率与同时使用的模型组合。
5. 部署、售后、云资源预算及开发/测试人员安排。

价格与首批场景确定后，应重新筛选同价位竞品和功能优先级；本文不作为交付工期或性能承诺。
